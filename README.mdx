# Ppx_deriver_kit


# `ppx-deriver-kit`

A helper for writing ppx derivers such as `enumerate` (e.g. `[@@deriving enumerate]`).
This library provides a framework that does most of the boilerplate work of writing a new
ppx deriver. A centralized library has the benefit of making it easier to add shared
improvements to multiple ppx's at once, and it helps standardize the implementation of ppx
derivers.

## Usage examples

`example/ppx/count.ml` defines `ppx_count`.
This is a ppx rewriter that creates a function to produce the "count" of a value, which
is its size (in an ad hoc sense). An example is:

```ocaml env=basic
open Ppx_deriver_kit_example_runtime.Export

type t =
  | Foo
  | Bar of bool
  | Baz of [`A | `B of unit option]
[@@deriving count]
```

The function works as follows:

```ocaml env=basic
# count Foo;;
- : int = 1
# count (Bar true);;
- : int = 2
# count (Bar false);;
- : int = 2
# count (Baz `A);;
- : int = 2
# count (Baz (`B None));;
- : int = 3
# count (Baz (`B (Some ())));;
- : int = 4
```

## Writing a deriver

To write a ppx deriver, you need to implement the `S` module type and pass it to
`Ppx_deriver_kit.register`. This section will walk through parts of the examples of writing
`ppx_count` (see `example/ppx/count.ml` for the full
implementation).

The kit will handle the recursion over the input type declaration, so we just need to
supply one callback per shape of type. For `ppx_count`, our internal representation is
`pattern * expression`: a pattern destructuring the value, and an expression
computing its count. `to_fn` wraps these parts in `fun`.

<!-- $MDX file=example/ppx/count.ml,part=count-info -->
```ocaml
  type t = pattern * expression

  let to_fn ~loc (pat, body) = [%expr fun [%p pat] -> [%e body]]
```

We also define names for the deriver, the ppx itself, and the `[%...]` extension, along
with the names and types of derived values.

<!-- $MDX file=example/ppx/count.ml,part=count-names -->
```ocaml
  let deriver_name = "count"
  let ppx_name = "ppx_count"
  let extension_name = deriver_name

  let derived_value_name type_name =
    match Ppx_helpers.mangle_unboxed type_name with
    | "t" -> "count"
    | "t_u" -> "count_u"
    | type_name -> "count_" ^ type_name
  ;;

  let derived_type ~loc core_type = [%type: [%t core_type] -> Stdlib.Int.t]
```

Modules `Signature_config` and `Structure_config` determine configuration types based on
deriver arguments. In this case we have none, but see documentation for
[`Ppx_helpers.Deriving_args`](../ppx_helpers/doc/deriving_args.mdx) for how this works.

<!-- $MDX file=example/ppx/count.ml,part=args-info -->
```ocaml
  module Signature_config = struct
    type t = unit

    let args = Ppx_helpers.Deriving_args.no_args
  end

  module Structure_config = struct
    type t = unit

    let args = Ppx_helpers.Deriving_args.no_args
  end
```

Each `on_*` callback handles one case of `core_type` or `type_declaration`.
Here is how `ppx_count` handles named types: in this case, we call the `count`
function corresponding to the named type, and then we use `core_type` to type annotate
the expression.

The callback returns a `(t, string loc) result`, where `t` is the type of the result if
this callback is successful and `string loc` is the error message and its location if the
callback fails. The error message is presented as `"<ppx_name>: <string>"`.

<!-- $MDX file=example/ppx/count.ml,part=named-type -->
```ocaml
  let on_named_type ~loc ~config:() ~core_type id params =
    let name = gen_symbol () in
    let expr =
      [%expr
        ([%e
           List.map params ~f:(fun param -> to_fn ~loc param)
           |> type_constr_conv ~loc id ~f:derived_value_name]
         : [%t derived_type ~loc core_type])]
    in
    Ok (pvar ~loc name, [%expr [%e expr] [%e evar ~loc name]])
  ;;
```

`on_tuple` is passed the `t` computed for each part, along with its label.

<!-- $MDX file=example/ppx/count.ml,part=tuple -->
```ocaml
  let on_tuple ~loc ~config:() ~core_type:_ ~unboxed tuple =
    let labeled_pats, counts =
      List.map tuple ~f:(fun (label, (pat, count)) -> (label, pat), count) |> List.unzip
    in
    let pat =
      if unboxed
      then ppat_unboxed_tuple ~loc labeled_pats Closed
      else ppat_tuple ~loc labeled_pats Closed
    in
    Ok (pat, sum_int_exprs ~loc (block_overhead ~loc ~unboxed counts))
  ;;
```

Finally, we determine how to turn the derived `t` values into generated code.

<!-- $MDX file=example/ppx/count.ml,part=struct-registration -->
```ocaml
  let to_structure_items ~loc ~config:() rec_flag tds_and_results =
    List.map tds_and_results ~f:(fun (td, result) ->
      let loc = { td.ptype_loc with loc_ghost = true } in
      let pat = pvar ~loc (derived_value_name td.ptype_name.txt) in
      let expr =
        eabstract
          ~loc
          (Ppx_helpers.type_param_conv_pats
             ~param_name:count_var_name
             ~param_type:derived_type
             td)
          (to_fn ~loc result)
      in
      let ty =
        combinator_type_of_type_declaration td ~f:derived_type
        |> Ppxlib_jane.Ast_builder.Default.ptyp_poly
             ~loc
             (List.map td.ptype_params ~f:Ppxlib_jane.get_type_param_name_and_jkind)
      in
      value_binding
        ~loc
        ~pat
        ~expr
        ~constraint_:(Some (Pvc_constraint { locally_abstract_univars = []; typ = ty }))
        ~modes:[])
    |> pstr_value_list ~loc rec_flag
    |> Result.return
  ;;
```

We don't need to specify anything like this for the signature as it can be automatically
created based on the type of the derived value. Finally, we register the deriver like so:

<!-- $MDX file=example/ppx/count.ml,part=registration -->
```ocaml
let () = Ppx_deriver_kit.register (module Count_info) |> Deriving.ignore
```

And this will let us use `ppx_count` both as a deriver on a type and inline as an
extension.

## Supporting extensions

A deriver built with the kit must also expand as an extension, reusing the
same callbacks to derive a value for a standalone core type rather than a type
declaration. `ppx_count` supports this by specifying its name, config, and expansion
function.

<!-- $MDX file=example/ppx/count.ml,part=extension -->
```ocaml
  let extension_config = ()

  let expand_extension ~loc ~core_type counted =
    Ok (pexp_constraint ~loc (to_fn ~loc counted) (Some (derived_type ~loc core_type)) [])
  ;;
```

The extension can be used like so:

```ocaml env=basic
# [%count: bool * string] (true, "hello");;
- : int = 7
```

The extension name can be the same or different from the deriver name.

## Supporting implicit unboxed types

Some types have an implicit unboxed version, such as a record type `t` having an unboxed
representation named `t#`. Sometimes, a deriver might want to generate values for both of
these representations:

```ocaml env=basic
type t = { x : int } [@@deriving count ~unboxed]
```

By setting the following flag to `true`, `ppx_count` will generate `count : t -> int` and
`count_u : t# -> int`, and `~unboxed` will be automatically registered as a flag in both
the structure and signature. It will not be present in the user's `config`s.

<!-- $MDX file=example/ppx/count.ml,part=support-unboxed -->
```ocaml
  let support_unboxed = true
```

## Code organization

- `src/ppx_deriver_kit_intf.ml`: contains the definitions of the types passed to callbacks
  and the module that the deriver is built from.
- `src/ppx_deriver_kit.ml`: contains the recursion over the input types and the
  registration logic behind `register`
- `example/ppx/count.ml`: an implementation of `ppx_count`
